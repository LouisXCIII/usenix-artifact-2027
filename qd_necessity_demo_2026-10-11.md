# Necessity demonstration: a destination-local Cedar/OPA policy cannot soundly re-derive the risk-tier $R_P$ instance (2026-10-11)

> **Scope correction (2026-10-11, same day, after a further external review).** This
> experiment shows that *some* proof/light-client verification layer $V$ is required before
> a `minMargin`/tier claim can be trusted by any destination -- ADP's own chaincode or a
> Cedar/OPA-based one alike. It does **not** show that $R_P$/$M_I$ specifically is necessary
> as opposed to a hand-written Cedar/OPA policy that consumes $V$'s already-authenticated
> output (i.e. Cedar/OPA placed *behind* the same verifier ADP uses). The reviewer's point:
> conflating "$V$ is required" with "ADP is necessary beyond $V$" is a real gap in the
> original framing of this file and of the manuscript paragraph it fed, both now corrected to
> state only the narrower, actually-established claim. The right experiment for the necessity
> claim is a three-arm comparison (Cedar+$V$, OPA+$V$ -- each with a naive and a hardened
> policy author -- vs.\ ADP, all three given $V$'s identical authenticated-attribute output)
> across four scenario families (mapping error, obligation, multi-hop freshness,
> cross-vocabulary widening) with non-circular ground truth; that comparison has not been run.
> This file's forged-proof result is retained below as what it actually established, and as
> the reason $V$ itself is out of scope for that comparison (both arms need it identically).

Step 4 of the agreed 6-step roadmap (synthesis review, same day): show that a local policy
engine (Cedar/OPA), given only destination-local inputs, cannot perform the risk-tier check
performed by `chaincode/risk_tier.go`'s `SubmitDecisionRiskTierVerified` without the source's
secret ZK-protected ML computation. This file documents what was actually tried and measured,
using the real Cedar engine and the real OPA engine, not a description of what they probably
cannot do.

## Question

`SubmitDecisionRiskTierVerified` (real deployed entry point, `chaincode/risk_tier.go:116-168`)
takes exactly: `decisionID, role, amount, proofJSON, publicSignalsJSON`. It runs a Groth16
pairing check (`verifyGroth16`, `zkverify.go`, using `github.com/consensys/gnark-crypto/ecc/bn254`
and the embedded v6 verification key) against `proofJSON`/`publicSignalsJSON`, and only after that
check passes does it read `public[4]` (the prover-declared `minMargin` floor) to derive the
achieved tier (`tierFromFloorSignal`) and apply the real `tierFractionBps`/`RoleThreshold` gate.
The function's own comment is explicit about what it never sees: "this function never sees the
achieved margin itself, only which floor the prover chose to prove against" -- and the margin
itself (and the 256-dim quantized feature vector it is computed from) is a Groth16 *witness*,
never a public signal, never transmitted in any message to the destination.

Could a destination-local PDP -- Cedar or OPA, evaluating a policy over whatever a real request
to this system actually carries -- perform the same job on its own, without delegating to a
pairing-check verifier?

## Method

Rather than reason about Cedar/OPA's capabilities from documentation or memory, this used the
real engines:
- **OPA v0.70.0**, official static Linux binary (`openpolicyagent.org/downloads/v0.70.0/opa_linux_amd64_static`).
- **Cedar v4.13.0**, the official `cedar-policy` Rust crate (AWS's own implementation, the same
  one used in AWS Verified Permissions), via a small Cargo project.

And a real forged-proof input, built from proof/public-signal files already on disk from the
earlier Tru-4 risk-tier work (`~/pqc-hardhat/experiments/portability/x16_out/`,
`tier1_example_T1_{proof,public}.json` -- a real, valid Groth16 proof, genuinely generated by
`x16_risk_tier_proofs.py` for the real corpus contract `09_mishandled_exception_vuln.sol`
(real margin 3.2478, barely clears the T1 floor 54,445,422, legitimately fails T2/T3)):

1. **Sanity check**: `snarkjs groth16 verify verification_key_v6.json real_valid_T1_public.json
   real_valid_T1_proof.json` -> `snarkJS: OK!` (the real proof is genuinely valid for its own,
   real public signals).
2. **Forgery attempt**: copy the public-signals file, overwrite index 4 (the `minMargin` floor
   signal) from `"54445422"` (T1, what this proof actually proves) to `"83886080"` (T3, a much
   stronger claim), keep the proof bytes (`pi_a`,`pi_b`,`pi_c`) byte-for-byte unchanged. This is
   the simplest forgery a dishonest prover or a compromised relay could attempt: splice a bigger
   floor into the public inputs without re-running the real ML inference or regenerating a real
   witness for that floor.
3. **Verify the forgery with the real verifier**: `snarkjs groth16 verify verification_key_v6.json
   forged_T3_public.json forged_T3_proof.json` -> `[ERROR] snarkJS: Invalid proof`. Exactly as
   Groth16's soundness property predicts: the proof is cryptographically bound to the full public
   input vector through the verification equation's linear-combination term (`vkx`/`IC`), not just
   to a "floor passed/failed" bit, so changing any public signal without re-proving breaks
   verification. `snarkjs` implements the identical Groth16 verification algorithm as the
   chaincode's `verifyGroth16`/`bn254.PairingCheck` (both are standard, unambiguous BN254 pairing
   checks over the same verification key); it is also the same tool this project's own proof
   generator (`x16_risk_tier_proofs.py`) already calls to confirm proof validity, so using it here
   reuses the project's own reference implementation rather than introducing a new one.
4. **Port the real chaincode's non-cryptographic logic, faithfully, to each engine.**
   `risk_tier_policy.rego` (OPA) ports `tierFromFloorSignal` and the
   `tierFractionBps`/`RoleThreshold` gate line-for-line, operating on a bare `input.declaredFloor`
   attribute (exactly what a destination-local PDP would have *if* it only received the floor
   claim and not the proof). `policies.cedar` (Cedar) ports the same logic for the `director` role
   only (matching the one role/amount pair tested here; not claimed as a full 5-role port).
   Neither file contains, or could be made to contain, a check that `declaredFloor` was itself the
   output of a genuine Groth16 verification -- that check is what step 3 above already performed,
   entirely outside both engines, in Go using `gnark-crypto`.
5. **Feed both engines the forged claim and the honest claim**, holding role=`director`,
   amount=`1800000` fixed (the same role/amount pair as the real, legitimate on-chain case
   `tier4-c1-tier3-safe`, `evidence/rp_checker_tier_2026-10-11/risktier_onchain_results_2026-10-11.json`):
   - forged: `declaredFloor=83886080` (claims T3; this is the floor value from the forged,
     cryptographically-INVALID public-signal file from step 3).
   - honest: `declaredFloor=54445422` (T1; what this exact proof was actually, legitimately
     generated for).

## Results (real, measured, both engines)

| Engine | input | declaredFloor | snarkjs verdict on the underlying proof | engine's own decision |
|---|---|---|---|---|
| OPA v0.70.0 (`opa eval`) | forged | 83886080 (claims T3) | `Invalid proof` | **`"SAFE"`** |
| OPA v0.70.0 (`opa eval`) | honest | 54445422 (T1, real) | `OK!` | `"REJECT"` |
| Cedar v4.13.0 (`cedar-policy` crate) | forged | 83886080 (claims T3) | `Invalid proof` | **`Allow`** |
| Cedar v4.13.0 (`cedar-policy` crate) | honest | 54445422 (T1, real) | `OK!` | `Deny`|

Both real engines admit the amount (1,800,000, director's full tier-3-adjusted cap of 2,000,000)
against a proof that the real Groth16 verifier has already, independently, rejected as invalid --
and both correctly reject the same amount against the floor the proof was actually, legitimately
generated for. The only difference between the two rows for each engine is one integer
(`declaredFloor`) that the caller supplies; neither engine has any way to check that integer
against the cryptographic evidence it is supposed to summarize.

## What this does and does not establish

**Established, with real measurement**: for this specific attack (splice a larger `minMargin`
floor into a genuine proof's public signals without re-proving), a destination-local policy
engine evaluating only the floor claim as a bare attribute is fooled into granting the full
tier-3 cap, while the real on-chain verification path (Groth16 pairing check, done in Go before
the tier is ever treated as a destination-local fact) correctly rejects the identical forged
input. This is a real, reproducible instance of the general necessity claim, not an appeal to
Cedar/OPA's documented feature lists: the actual, official engines were run, on a real forged
Groth16 proof, and both actually returned the unsafe decision.

**Not established**: this is one forgery strategy (public-input splice without re-proving) on
one role/amount pair, not an exhaustive search over forgery strategies or over `RoleThreshold`'s
other four roles (the Cedar port only encodes `director`; the OPA port's constants cover all five
roles but only `director` was exercised here). It also does not show that NO possible Cedar/OPA
policy could ever express a pairing check -- Rego is general-purpose enough that a sufficiently
determined author could, in principle, hand-implement BN254 field and pairing arithmetic as Rego
rules (slow, and not using any built-in cryptographic primitive Rego ships); this was not
attempted, and is not where this experiment's claim rests. The claim is about the real, intended
use of these engines as policy-decision points over given facts, not about Rego's Turing-power in
the limit, and about what is structurally transmitted to the destination in this real protocol
(never the margin/feature vector, never the Groth16 witness) versus what a policy engine could do
if, hypothetically, it were handed that data directly -- which this system's privacy design
deliberately avoids doing.

**Relation to $R_P$**: this gives empirical teeth to why $\gamma_d$ (the tier-based classification)
must be established via $M_I$ applied to the source-attested, proof-verified tier (an authorization
decision ported from the source, per this paper's $R_P$ model) rather than re-derived by a
destination-local PDP evaluating its own policy over locally-available or caller-supplied facts:
the evidence that would let a local PDP re-derive $\gamma_d$ soundly (the real margin, authenticated
against the real ZK witness) never reaches the destination's attribute schema, and the one
attribute that does reach it (the declared floor) cannot be authenticated by a policy-evaluation
engine on its own.
