# S9 results: dictionary-attack identification precision, side-channel check, independent red-team pass (2026-09-29)

Protocol: `s9_dictionary_attack_protocol_2026-09-29.md` (frozen before any query or analysis; no amendments). Files: `s9_dictionary_attack/` (`s9_a1_offline.json`, `s9_a2_offline.json`, `s9_a3_sample.json`, `s9_a3_query.js`, `s9_a3_result.json`, `s9_b_result.json`, `s9_b_s8_result.json`). No AI-generated adversarial content anywhere in this experiment.

## Measure A1: collision structure across the full 643-contract corpus (offline)
- codeHash (SHA-256 of raw source): **0 collision groups** across all 643 contracts (every source is a unique 253-bit value; no two distinct corpus files share a codeHash).
- featureHash (Poseidon of quantised x): **25 collision groups, 61 contracts** (unchanged from S8; re-verified here).

## Measure A2: identification precision for the 189 real committed decisions
For each of the 189 decisions actually committed on the live Besu registry (22 from S4 + 167 from S8), we asked: if an attacker has only the on-chain featureHash and a candidate pool of the full 643-contract corpus, how many candidates share that hash?
- Mean group size: 1.46; median: 1.
- **76.7% (145/189) of real committed decisions are uniquely identified** by featureHash alone against this candidate pool (group size 1).
- Mean identification precision (1/group size, averaged per decision): **85.4%**.
- Worst case: one decision falls in a group of 5 (precision 20%).
This is the first quantified "how good is the attack" number in this project; S5/S8 had only reported the raw collision count (61/643), not what an attacker achieves against the actual committed decisions.

## Measure A3: real read-only dictionary-attack query against the live registry
For 50 corpus contracts NOT among the 189 committed (random sample, seed 20260929), we computed their real codeHash/featureHash and queried the live `RegistryContract.mlScanPassed` and `FeatureCommitRegistry.featureHash` view functions on the running Besu chain (`eth_call`, no transaction, no gas, no state change). **0/50 false hits**: every uncommitted candidate correctly reads back `mlScanPassed=false` and `featureHash=0x0`. An attacker scanning candidates that are not the true source gets no false confirmation from the live contract state.

## Measure B: side-channel check (argument byte size vs. source properties)
- **S7 (n=22):** argument bytes vs. real source-file byte length: Spearman rho=0.448, p=0.036 (nominal). Argument bytes vs. margin: rho=0.061, p=0.787. Bytes vs. registration order: rho=-0.269, p=0.225 (not the explanation; registration order itself does not correlate with source length, p=0.813, ruling out an MPT-trie-growth confound).
- **S8 (n=173, argument bytes reconstructed offline and deterministically from the same real proofs/headers already used on-chain -- no new transactions sent):** argument bytes vs. real source-file byte length: rho=-0.143, p=0.060. Bytes vs. margin: rho=0.071, p=0.354.
- **Reading:** the S7 finding (nominal p=0.036 on n=22, two comparisons tested, does not survive even a mild Bonferroni correction at alpha=0.05/2=0.025) did **not replicate** at n=173 in S8 -- the sign even flips and stays non-significant. The weight of evidence is that argument byte size does not leak source length or margin; the S7 result is best read as a small-sample fluctuation, disclosed rather than treated as a real channel because it was the pre-registered check.

## Measure C: independent red-team pass
A fresh agent, given only the chaincode source and the S7/S8 results files (not this protocol), was asked to find any leakage path beyond the two published digests. It read all six assigned files plus, on its own initiative, `s4_b1_entrypoints.go`, `policy_scale_sweep.go`, and the built chaincode packages on disk. Its two findings were independently re-verified below (source line checks and a live, read-only `peer lifecycle chaincode queryinstalled`/`querycommitted` query); nothing was accepted on the agent's word alone.

### Finding 1 (CONFIRMED, HIGH severity): the raw model weights are shipped in plaintext in the exact chaincode package installed and committed on the real channel used for this paper's evidence
`b1fair.go:18-19` embeds `b1_model_weights.json` (the raw quantised `W`, `b` matrix, not a digest) via `//go:embed`, in the same Go package directory as every production entry point. Independent verification:
- `sha256sum ~/authcc-network/fabric-samples/test-network/authcc.tar.gz` = `43d5989945470668ac77625f6662d8942d2d388fa63eb25b22cd9342f81e9ca0`.
- `peer lifecycle chaincode queryinstalled` lists exactly that package ID under label `authcc_2.29` as installed on the peer.
- `peer lifecycle chaincode querycommitted -C authchannel` shows `Name: authcc, Version: 2.29, Sequence: 41` committed on the real channel.
All three identifiers match: **the package containing the plaintext weights is not a hypothetical risk -- it is the exact chaincode currently installed and committed on the real `authchannel` used for every experiment in this paper (S4 through S9).** Any peer administrator of an endorsing organisation who has installed this chaincode (required to endorse any transaction on this channel) has direct filesystem access to `W` and `b`, independent of whether their organisation ever invokes a B1 baseline entry point. This is a broader exposure than "the destination's decision logic never receives `W`" (which remains true of the on-chain data path: S7/S8's block-byte search covers exactly that path and found nothing) -- it is a packaging/distribution exposure to peer administrators, a surface S7/S8 did not examine because both scoped their search to committed ledger bytes, not the installed chaincode package. Root cause: the B1 fairness baseline (`b1fair.go`, deliberately non-private by design, disclosed in `s4_fair_b1_results_2026-09-28.md`) was added to the same Go package as the production ADP path rather than a separately packaged module, so Fabric's package-then-build-from-source mechanism ships the weights file to every installer regardless of which entry points that installer calls.

**FIXED, verified live (2026-09-29).** The user chose to fix rather than only disclose. Confirmed no production file references any of the four items (`grep -rln` across the whole chaincode package returned nothing outside `b1fair.go`/`poseidon_opt.go`/`s4_b1_entrypoints.go` themselves), and that `poseidon_opt.go` is never called from the production path (only comments in `zkverify.go`/`featurebind.go` mention Poseidon; no call sites). A clean staged copy of the chaincode source was built excluding `b1fair.go`, `poseidon_opt.go`, `s4_b1_entrypoints.go`, and `b1_model_weights.json`; it compiled cleanly (`go build ./...`, exit 0) and a residual-reference grep after exclusion was empty. Packaged and deployed as `authcc` version `2.30`, sequence `42`, on the real `authchannel` (both organisations approved and committed). Verification performed on the live, running system, not assumed:
- `peer lifecycle chaincode getinstalledpackage` retrieved the package actually installed on the peer (ID `authcc_2.30:fc31d84d...`, matching what was committed) and extracting it confirms `b1_model_weights.json`, `b1fair.go`, `poseidon_opt.go`, and `s4_b1_entrypoints.go` are **absent from the real installed package**.
- `SubmitDecisionB1Store` now returns `"Function SubmitDecisionB1Store not found in contract AuthContract"` -- the entry point is gone from the running chaincode, not just from a file listing.
- `ReadDecision` on a real S8 decision ID (`s8-t-c000-1790605271`) returns its original record unchanged -- all prior evidence (S4 through S9) remains readable after the upgrade.
- `GetRoleThreshold` and other production reads continue to work normally.
This closes Finding 1 for any future query of this channel; it does not retroactively remove `W` from the previously-installed `authcc_2.29` package file that a peer administrator may already have had on disk before this fix, which is a residual, disclosed fact (a filesystem artifact of the prior package, not a live channel exposure going forward).

### Finding 2 (plausible lead, NOT measured): a possible timing side-channel in the B1 Timed entry points
`b1Relation` (`b1fair.go:112-138`, independently re-read) computes all 12 classes' logits unconditionally in its first loop (an early return there only fires on a rare comparator-domain overflow, not in normal operation), but its second loop -- checking each non-winning class's margin -- returns as soon as it finds the first class whose margin is too small, so the number of iterations before return depends on `x` and `W`. The `*Timed` entry points (`s4_b1_entrypoints.go`) expose a `VerifyNs` field isolating exactly this computation via `time.Since()`, committed to the ledger and readable by any channel member. The loop body is a single comparison per iteration over at most 12 classes, so the plausible signal is very small and likely below Fabric/gRPC measurement noise; this was not timed or measured, and is reported as an unvalidated lead, not a finding.

### Clarification (not a new leak): the `minMargin`/`minConfidence` public signal is a raw quantised number, not a digest
`public[4]` (`zkverify.go`) is a real-valued function of `x`,`W` (winning logit minus runner-up), supplied by the caller as a circuit-declared public input before the chaincode runs, and echoed verbatim into the ledger on a margin-failure REJECT. This is not a new disclosure created by the chaincode (the value is public by circuit design, same class as `class`/`pred`, already discussed in S4/S5), but the protocol description "digests, not raw values" undersells this one signal; it is a circuit/protocol scoping note, not a chaincode bug.

### Checked and clean
Header/MPT verification (`lightclient.go`), feature-binding (`featurebind.go`), proof verification (`zkverify.go`), the decision record and all mutators (`authchaincode.go`), and the Poseidon implementation (`poseidon_opt.go`) were read in full: no logging, no error string, and no stored/returned field carries `x`, `W`, or source text beyond the two intended digests and already-public signals. No hidden getter or debug entry point exists anywhere in the package beyond the already-known, intentionally-`x`-taking B1 entry points.

## What this does not show
- codeHash collision-freeness is empirical over 643 SHA-256 outputs, not a general cryptographic collision-resistance proof (expected, not a new assumption).
- The side-channel check covers only argument byte size on already-collected data; it does not cover gas cost, block timing, or any covert channel outside what S7/S8 measured.
- Measure C is one fresh reviewer, read-only, source-only; it is a lead-generation pass like the earlier security-audit run in this project, not an exhaustive proof of no leakage.
