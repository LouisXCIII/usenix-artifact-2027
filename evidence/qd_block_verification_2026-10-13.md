# Independent, signature-verified block evidence for obligation-coverage (replaces the 2026-10-12 "Mức 1" snapshot+hash design)

## Why this replaces `qd_advisor_independent_2026-10-12/`

That package's `cases.json` used synthetic decisionIds and a JSON file whose only integrity
guarantee was a hash computed by the paper's own author — it proves a file wasn't edited after
export, not that its content came from the real ledger. The intended audience for independent
verification is primarily USENIX reviewers / artifact evaluation, who will never connect to this
project's live network, so a design requiring a live connection ("Mức 2") was also dropped rather
than built (see plan file, 2026-10-13 entry, for the full reasoning).

This package instead exports **raw, cryptographically signed Fabric blocks** — the channel's own
endorsement and orderer signatures, checkable with nothing but the channel's own root CA
certificates and standard Go crypto.

**Honest framing (corrected 2026-10-13, after review):** "The exported blocks are verifiable for
integrity and internal consistency (signatures, hash chain, recovered state) without the
authors' tooling; because all signing identities belong to a single administrative domain, they
do not constitute third-party attestation." Every CA here (Org1MSP, Org2MSP, OrdererMSP) was
generated by this project's own `cryptogen`/Fabric CA setup, under the same operator as the
decisions themselves — so a sufficiently determined author could in principle have fabricated an
entire self-consistent chain. What this package actually establishes is that the data was not
altered by anyone WITHOUT access to those signing keys (a real, checkable property), not that it
is independent of the authors (a stronger claim this package does not make).

## What's in this package

- `blocks/` — 25 consecutive raw `.block` files (height 5081–5105) plus `genesis.block`
  (channel genesis, for context). Fetched via `peer channel fetch <N> ...`.
- `certs/` — root CA certs for `Org1MSP`, `Org2MSP`, `OrdererMSP` (the channel's MSP trust roots).
- `verifier/` — standalone Go module, `go build .` then `./qdblockverify verify ../blocks ../certs`
  or `./qdblockverify recover ../blocks <decisionId...>`. Imports only the public
  `fabric-protos-go-apiv2` schema — no project chaincode code.
- `run_s5s6s7_real.py`, `run_clean_cd_reuse_real.py` — the scripts that produced the real
  transactions below (for provenance; not needed to verify, only to see how the data was made).
- `reuse_guard_gap_finding_and_fix.md` — a real chaincode bug found and fixed while building
  this package (see below).

## Finding + fix made while building this package

Two real issues were found and fixed while producing this evidence, both disclosed in full:

1. **Chaincode**: `SubmitDecisionTrustlessV7ObligationVerifiedDischarge` was missing the
   reuse/double-citation guard that its sibling `...DomainVerified` already had (2026-10-08 fix
   never backported). Fixed, deployed as v2.43/seq55, re-verified live (see
   `reuse_guard_gap_finding_and_fix.md`).
2. **This verifier itself**: the mandatory negative/tamper test (flip one byte in a block copy,
   confirm `verify` reports FAIL) initially did **not** catch the tampering — the first version
   checked endorsement + orderer signatures and the header hash-chain, but never checked the
   block's own `DataHash` against its actual `Data`, so a byte flipped outside the
   endorsement-signed bytes (e.g. in `ChaincodeProposalPayload`) went undetected even though every
   signature still verified. Root cause confirmed empirically (DataHash = `sha256` of the
   concatenated raw envelope bytes, verified against 4 real blocks before relying on it) and fixed
   by adding that check. Re-ran both tests after the fix:
   - 25/25 real blocks → PASS.
   - The same byte-flipped block → FAIL, with the exact `DataHash mismatch` error.

## Update (same day, after external review): verifier restructured + 3 more real findings

The verifier now runs and reports every check (dataHash, endorsements, endorsementPolicy,
ordererSig, validationFilter, hashChain) **independently** — it never stops at the first
failure, so any FAIL is attributable to the exact check that caught it (see
`negative_tests/README.md` for 4 new isolated negative-test cases, on top of the original
byte-flip). Two more real, disclosed findings from this restructuring:

- **Endorsement policy** is channel-default `MAJORITY Endorsement` with 2 orgs
  (Org1MSP+Org2MSP) — but this only applies to the real `authcc` chaincode. Applying it
  blindly to every transaction initially mis-flagged 2 real blocks (5099-5100) as FAIL — those
  are `_lifecycle` chaincode-approval transactions, which are legitimately single-org-endorsed
  by design (each org submits its own `approveformyorg` call). Fixed by checking the
  invoked chaincode's name and only enforcing the 2-org requirement for `authcc`.
- **`TRANSACTIONS_FILTER` was absent from every block as originally fetched** via
  `peer channel fetch`, confirmed empirically: that command retrieves blocks via the
  **orderer's** deliver service, and Fabric's orderer never validates transactions — only a
  **peer's own ledger copy**, after independently validating and committing, carries real
  per-transaction validation codes. **Update, same day, after a second external review**: a
  peer's own copy IS retrievable, via the `qscc` system chaincode
  (`peer chaincode query -C authchannel -n qscc -c '{"Args":["GetBlockByNumber","authchannel",<N>]}'`,
  stripping the trailing newline `peer chaincode query` appends to its raw payload). Confirmed
  directly on block 5081 before trusting it further: header, `Data`, and all signatures in the
  `qscc` copy are byte-identical to the orderer-delivered copy; only `TRANSACTIONS_FILTER` (now
  a real per-tx code, `0x00`/VALID in every case observed) and `COMMIT_HASH` (a peer-only slot
  this verifier does not check) differ. All 25 blocks were re-fetched this way and now ship as
  this artifact's canonical `blocks/`; the original orderer-fetched copies are kept, superseded,
  under `blocks/_orderer_fetched_superseded/`. Re-running the verifier against the re-fetched
  blocks: **25/25 blocks PASS, 6/6 checks PASS on every block** — `validationFilter` is no
  longer `N/A` for any block in this artifact. The three-way PASS/N/A/FAIL return in
  `computeTxValidity` is kept in the verifier's code, since a caller who points it at an
  orderer-fetched block (as this artifact's first pass did) still needs that honest distinction.

## How to verify the cryptography independently (not independent of the authors' signing keys — see framing above)

```
cd verifier
go mod tidy        # pulls only fabric-protos-go-apiv2 + google.golang.org/protobuf
go build .
./qdblockverify verify ../blocks ../certs
./qdblockverify recover ../blocks qd3-clean-verified-1791859258 qd3-s7-verified-1791859143
```
`verify` must print `25/25 blocks PASS`. `recover` must print the exact JSON
`PortableDecisionRecord` that was really `PutState`-written on-chain for each key, decoded
directly from the block's own read-write set — not from any file this project's author supplied.
