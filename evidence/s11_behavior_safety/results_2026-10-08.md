# S11 results: closing the "behavior-safety beyond policy-safety" gap (2026-10-08)

Source of the finding: direct source reading of `~/fabric-network/authcc/chaincode/obligation_v2.go`
and `v7_obligation.go` (prompted by the paper's own Table 8 "Behavior-safety beyond policy-safety"
row, added the same day). `SubmitDecisionObligationV2` and `SubmitDecisionTrustlessV7Obligation`
both take `obligationDischarged`/`enforcementWitnessVerified` as **raw caller-supplied booleans**,
fed straight into `oblCoveredV2()` with no cross-check against any real on-chain discharge event.
The only real discharge mechanism, `DischargeObligation` (`authchaincode.go:480`), flips *only its
own record's* `ObligationDischarged` field -- confirmed by `grep ObligationDischarged chaincode/*.go`
that `obligation_v2.go`/`v7_obligation.go` never read that field back. A caller can therefore claim
`obligationDischarged=true` for a transfer whose obligation was never discharged anywhere on-chain,
and the destination classifies it `SAFE` on real `semBound`/`evOK`/role/amount alone: policy-safe
(every existing check passes) but not behavior-safe (the real-world precondition the `SAFE` label
is supposed to certify is unverified). This is distinct from, and not closed by, S10 (2026-10-04):
S10 made `semBound`/`evOK` real (derived from a proof) in `SubmitDecisionTrustlessV7Obligation`, but
left the *obligation-discharge* claim itself exactly as caller-trusted as before.

## Fix

New file `~/fabric-network/authcc/chaincode/ablation_behavior_safety.go`, function
`SubmitDecisionTrustlessV7ObligationVerifiedDischarge`. Additive -- changes neither
`SubmitDecisionTrustlessV7Obligation` (v7_obligation.go) nor `SubmitDecisionObligationV2`
(obligation_v2.go). It re-runs V7Obligation's exact evidence-chain and obligation-model pipeline
unchanged, but replaces the caller-supplied `obligationDischarged` boolean with a real `GetState`
lookup of a referenced decision record (`obligationDischargeRef`), requiring that record to:

1. actually exist on-chain and have `ObligationDischarged=true` (set only by the real
   `DischargeObligation` state transition), **and**
2. be bound to the *same* transfer being submitted here (`sourceDomain`, `role`, and `amount` of
   the referenced record must match this decision's claimed values) -- closing both the "claim was
   never true" gap and the "claim was true for a different, unrelated transfer" confused-deputy
   variant of it.

`enforcementWitnessVerified` remains a caller-supplied boolean: this codebase has no independent
enforcement-witness submission mechanism to verify it against, so that narrower claim (S7
laundering) stays an explicitly disclosed, unclosed residual limitation -- this fix closes the
discharge-claim half of the gap, not the witness-claim half.

`go build ./...`, `go vet ./...`, `go test ./...` (existing suite) all clean. Deployed as `authcc`
version `2.36`, sequence `48` on the real `authchannel` (both orgs approved and committed;
`peer lifecycle chaincode querycommitted` confirms). Confirmed live on-chain with a minimal
malformed-input smoke test (`codeHash` not 32 bytes of hex -> the exact validation error the new
code contains, not "function not found") before the real experiment below.

## Real experiment (`run.py`, `s11_result.json`)

Main-chain Besu had been down since before the host reboot (0 peers, stuck in IBFT round-change
since validator boot); recovered by re-establishing the `pqc_tunnel` mesh across all 4 validators,
waited for round-change to resolve naturally once peers connected (~43 minutes of accumulated
round-change backoff before mesh was up; block production resumed within a few minutes of all 4
peers connecting). `SetClock(now+300)` then a fresh header fetch (`s8_fetch.js`, block `654848`)
were run immediately before this experiment, so every proof/header used below is genuinely current.
Fixture: `03_dos_safe.sol` (`SAT[0]`, same real, distinct S4 contract S10 used). Six real
transactions were submitted via `peer chaincode invoke --waitForEvent` (mined, endorsed by both
orgs) plus one rejected replay attempt; `heightBefore=4767`, `heightAfter=4773` (exactly the 6
committed transactions, consistent).

**A. Exploit, reproduced live on the deployed, unmodified `SubmitDecisionTrustlessV7Obligation`
(v2.35/seq47).** Genuine proof + genuine header + `obligationProfile=audit, mappedMechanism=audit`
(sufficient mechanism strength) + `obligationDischarged=true, enforcementWitnessVerified=true` as a
**bare claim with zero real discharge event anywhere on-chain for this decision** ->
**`SAFE`** (`obligationDetailV2`: "obligation genuinely covered: correct mechanism, sufficient
strength, discharged, independently witnessed"). `gap_demonstrated: true`. This is a real,
mined transaction the deployed entry point wrongly accepted as behavior-safe.

**B. Same scenario, patched entry point, no real discharge reference.** Identical genuine
proof/header/profile/mechanism, submitted to `SubmitDecisionTrustlessV7ObligationVerifiedDischarge`
with `obligationDischargeRef=""` -> **`REJECT`** (`obligationDetailV2`: "obligation not yet
discharged ... [discharge: no obligationDischargeRef supplied (treated as not discharged)]").
`fix_confirmed: true`. The same forged claim that fooled the deployed entry point in case A is
rejected by the patched one.

**C. Legitimate path preserved.** A real `CONDITIONAL` decision is created
(`SubmitDecisionFull`, `role=manager, amount=300000` -- above the `requiresObligation` threshold of
`250000`, `secondApprovalObtained=false`) -> `CONDITIONAL` (real state). A real
`DischargeObligation` call on that same decision -> `EXACT` (real state transition,
`ObligationDischarged=true` now genuinely set on-chain). A *new* decision for the *same*
`sourceDomain/role/amount` (`300000`), referencing that real discharge via
`obligationDischargeRef`, submitted to the patched entry point -> **`SAFE`**.
`honest_path_preserved: true`. The fix does not break the honest case: a genuinely discharged
obligation is still recognized and still yields `SAFE`.

**D. Confused-deputy / cross-wiring rejected.** The *same* real discharged record from case C is
referenced by a *different* decision claiming `amount=310000` (not `300000`) -> **`REJECT`**
(`obligationDetailV2`: "... referenced record ... was discharged, but for a different transfer
(sourceDomain/role/amount mismatch) -- cannot cover this decision (confused-deputy rejected)").
`binding_check_confirmed: true`. A real, genuinely-discharged obligation cannot be "borrowed" to
cover an unrelated transfer.

**E. Replay sanity.** Re-submitting case B's `decisionId` to the patched entry point is rejected
(`"already recorded (replay rejected)"`) and `ReadDecision` before/after is byte-identical
(`recordUnchanged: true`) -- matches the existing fail-closed replay behaviour of every other
`Submit*` entry point.

## What this does and does not establish

This closes the specific gap as stated: a destination using
`SubmitDecisionTrustlessV7ObligationVerifiedDischarge` can no longer be fooled by a bare, unbacked
`obligationDischarged` claim, and a real discharge cannot be cross-wired to cover a different
transfer. It does not claim `SubmitDecisionObligationV2` or `SubmitDecisionTrustlessV7Obligation`
are deprecated or now unsafe to use standalone -- both remain available, and both still trust the
caller's discharge claim exactly as before; the new entry point is the stronger alternative for
destinations that want the discharge claim itself verified. It does **not** close the narrower,
separately-disclosed `enforcementWitnessVerified` (S7 laundering) gap: this codebase has no
independent witness-submission mechanism, so that boolean remains caller-asserted in both the old
and the new entry point. It also does not extend to `SubmitDecisionObligationV2`'s own
claim-trust weakness for `semBound`/`evAssuranceOK` (already characterized in S10 case C) -- that
is a separate, already-disclosed limitation of that specific entry point.
