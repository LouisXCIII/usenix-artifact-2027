# S10 independent red-team pass (2026-10-04)

Mirrors the S9 methodology: a fresh agent, given ONLY the chaincode source (`v7_obligation.go`,
`featurebind.go`, `lightclient.go`, `zkverify.go`, `obligation_v2.go`, `authchaincode.go`,
`clock.go`) -- NOT this project's test scripts, results, or design rationale -- was asked to find
any way to make `SubmitDecisionTrustlessV7Obligation` return SAFE/EXACT while either the evidence
chain or the obligation chain is actually false, or any other correctness bug, by reading the
source alone (no live testing by the agent itself).

## Findings (agent's own words, verbatim verdicts; file:line references are the agent's)

1. **Investigated, not exploitable** -- switch-case ordering (v7_obligation.go:101-114): Go's
   bare `switch{}` is first-match-wins, no fallthrough; `default: SAFE` is reached only when all
   five negated conditions are false. No reordering bug.
2. **Investigated, not exploitable** -- evidence-chain re-derivation (lines 48-89) is a
   byte-for-byte copy of `SubmitDecisionTrustlessV7`'s checks (7-signal requirement, codeHash
   substitution check, header freshness/quorum, feature binding); confirmed `ledgerNow(ctx)` is
   used, not the TOCTOU-vulnerable caller-supplied-timestamp variant from a different, separately
   named ablation function (`ablation_a9_toctou.go`). No check V7 has is dropped here.
3. **Investigated, not exploitable** -- `oblCoveredV2`'s map lookups (`requiredStrengthV2`,
   `mechanismStrengthV2`) are fail-closed: an unknown profile or mechanism returns `(false, ...)`,
   driving REJECT; Go's two-value map lookup correctly distinguishes "key absent" from "key
   present with value 0" in both tables, so there is no zero-value-for-unknown-key bypass.
4. **Investigated, not exploitable** -- TOCTOU/replay (`decisionExists` then `PutState`) matches
   every other entry point's pattern; double-submission races are caught by Fabric's own
   key-level MVCC, nothing specific to this function.
5. **Architectural caveat, flagged for visibility, NOT a new bug**: `obligationProfile`,
   `mappedMechanism`, `obligationDischarged`, `enforcementWitnessVerified` are plain
   caller-supplied values with no cryptographic binding to real source-domain obligation state
   (unlike `semBound`/`evOK`, which are proof-derived) -- a caller can pick
   `obligationProfile="empty"` to make `oblCoveredV2` trivially true. The agent correctly
   identified this is the SAME pre-existing trust model as `SubmitDecisionObligationV2`
   (obligation_v2.go), explicitly documented in this project's own file header ("does not invent
   any new verification primitive") -- i.e. known, disclosed scope, not a defect introduced by
   `SubmitDecisionTrustlessV7Obligation`.
6. **Unresolved/minor**: no dedicated `_test.go` exists for `SubmitDecisionTrustlessV7Obligation`.
   Follow-up check (by me, not the agent): neither `SubmitDecisionTrustlessV7` nor
   `SubmitDecisionObligationV2` -- the two functions this one composes -- has a dedicated unit
   test file either (`grep` across all `*_test.go` for both names: 0 hits). This whole family of
   entry points is validated through live Fabric integration runs (S7/S8/S10), not Go unit tests;
   the new function is consistent with that existing convention, not newly deficient relative to
   its siblings.

## Overall verdict (agent's words)

"After a thorough line-by-line read, I found no parameter combination, type confusion, map
zero-value trick, switch-ordering defect, or dropped V7 check that lets
`SubmitDecisionTrustlessV7Obligation` return SAFE/EXACT while either the evidence chain or the
obligation chain (as coded) is actually false; the one real weakness is the long-standing,
documented architectural one (obligation-chain inputs are caller-asserted, not proof-bound),
which is inherited unchanged from `SubmitDecisionObligationV2` rather than introduced by this
function."
