# S10 results: closing the 29/9 obligation/proof-chain completeness gap (2026-10-04)

Source of the finding: `report_generator/build_report.js` Muc 8 (Han che), bullet dated 29/9 --
no deployed entry point verified BOTH the real evidence chain (ZK proof + light-client header,
`SubmitDecisionTrustlessV7`) AND the real obligation chain (`oblCoveredV2`,
`SubmitDecisionObligationV2`) in the same transaction. `SubmitDecisionTrustlessV7`'s `classify()`
never consults any obligation model; `SubmitDecisionObligationV2` takes `semBound`/`evAssuranceOK`
as caller-supplied booleans, never re-deriving them from a proof. Confirmed by direct source
reading (grep across every `Submit*`/`SubmitHopDecision*` function signature in
`~/fabric-network/authcc/chaincode/*.go`): none combines a `headerJSON`/`registryProofJSON`
parameter with a `secondApprovalObtained`/`obligationProfile`/`mappedMechanism` parameter.

## Fix

New file `~/fabric-network/authcc/chaincode/v7_obligation.go`, function
`SubmitDecisionTrustlessV7Obligation`. Additive -- does not change `SubmitDecisionTrustlessV7`
(featurebind.go) or `SubmitDecisionObligationV2` (obligation_v2.go). It re-runs V7's exact
proof-chain pipeline (`verifySemBoundProof`, `verifySourceState`, `verifyFeatureBinding`) to
compute real `semBound`/`evOK`, then gates the final class on `oblCoveredV2` called with those
real values instead of a caller claim:

```
case !semBound:          REJECT  (Theorem T0)
case !evOK:              REJECT
case !roleKnown:         REEVALUATE
case amount > threshold: REJECT (widening)
case !oblCovered:        REJECT  (S5/S6/S7 -- new condition this entry point adds)
default:                 SAFE
```

`go build ./...` and `go vet ./...` clean; `go test ./...` (existing suite, including
`lightclient_test.go`'s header-verification fixtures and the formal obligation tests) passes
unchanged. Deployed as `authcc` version `2.31`, sequence `43` on the real `authchannel` (both
orgs approved and committed; `peer lifecycle chaincode querycommitted` confirms). Confirmed live
on-chain with a minimal malformed-input smoke test before the real experiment below (invoking
with a bad `codeHash` returns the exact validation error the new code contains, not a "function
not found" error -- the entry point is genuinely installed and reachable).

## Real experiment (`run.py`, `s10_result.json`)

Ledger clock was 5.15 days stale after the host reboot earlier the same day (`LedgerClock`
query: 1790652752 vs. real `date +%s` 1791097942); `s8_run.py setup` was re-run to `SetClock` and
fetch a fresh Besu header + Merkle-Patricia proofs for all 189 registered contracts (header
block 607318) before this experiment, so every proof/header used below is genuinely current, not
reused stale state. Fixture: `03_dos_safe.sol` (one of the 22 real, distinct S4 contracts, picked
as `SAT[0]`). Six real transactions were submitted via `peer chaincode invoke --waitForEvent`
(mined, endorsed by both orgs) plus one rejected replay attempt; `heightBefore`=4029,
`heightAfter`=4035 (exactly the 6 committed transactions, consistent).

**A. Agreement (no regression).** Genuine proof + genuine obligation
(`profile=audit, mechanism=audit, discharged=true, witnessVerified=true`):
`SubmitDecisionTrustlessV7` -> `SAFE`; `SubmitDecisionTrustlessV7Obligation` -> `SAFE`. The two
entry points agree on the happy path.

**B. S5/S6 divergence -- the gap that mattered.** The SAME genuine proof/header as above, but
`mappedMechanism=""` (obligation stripped, `profile=dual_approval`):
`SubmitDecisionTrustlessV7` (blind to obligation) -> **`SAFE`** -- the real gap, reproduced live;
`SubmitDecisionTrustlessV7Obligation` -> **`REJECT`** (`oblDetail`: "S5: obligation stripped").
`gap_demonstrated: true`. This is a real transaction a destination running only V7 would have
wrongly accepted, that the new combined entry point correctly rejects.

**C. Reverse divergence -- ObligationV2's claim-trust gap.**
`SubmitDecisionObligationV2` called with `semBound=true, evAssuranceOK=true` as a bare claim (no
proof argument exists on that function at all) plus genuine obligation parameters -> **`EXACT`**
(wrongly accepts; role is destination-native so identity-mapping applies). The same genuine
obligation parameters passed to `SubmitDecisionTrustlessV7Obligation`, but with the ZK proof
tampered (one digit flipped in `pi_a[0]`, the same `N2_tampered_proof` fixture mutation already
validated in S8) -> **`REJECT`** (`semBound=false` because the real proof fails verification,
regardless of how good the obligation claim looks). `gap_demonstrated: true`. The new entry point
cannot be fooled by a bare claim the way `SubmitDecisionObligationV2` can, because `semBound` is
re-derived from a real proof on every call, never accepted as an argument.

**D. Replay sanity.** Re-submitting case A's `decisionId` to `SubmitDecisionTrustlessV7Obligation`
is rejected (`"already recorded (replay rejected)"`) and `ReadDecision` before/after is byte-identical
(`recordUnchanged: true`) -- matches the existing fail-closed replay behaviour of every other
`Submit*` entry point.

## What this does and does not establish

This closes the specific completeness gap as stated: a destination can now require, in one
transaction, that the evidence chain and the obligation chain both hold, and we have a real,
mined, on-chain case (B) where that combination changes the outcome versus either existing entry
point alone, plus a real case (C) showing the new entry point is not vulnerable to the
claim-trust weakness of `SubmitDecisionObligationV2`. It does not claim `SubmitDecisionObligationV2`
or `SubmitDecisionTrustlessV7` are themselves now deprecated or unsafe to use standalone -- both
remain correct for the narrower claims they were built to test (Ablation-style measurement of
each chain in isolation); `SubmitDecisionTrustlessV7Obligation` is an additional, stronger entry
point for destinations that want both guarantees in one decision. It also does not extend to the
two other open items in the same "3 điều cần biết" bullet (`SubmitDecisionFull` accepting
`amount<=0`; the 13 read-only code-review items) -- those remain open, unrelated gaps.
