# Disciplined naive-vs-hardened pilot, Groups 2-4 (obligation, multi-hop, cross-vocabulary)

**Date:** 2026-10-11. **Status:** preliminary pilot evidence, not a substitute for an
independent human-authored study. Continues `evidence/qd_pilot_2026-10-11.md` (Group 1,
mapping-error family) under the same user-specified protocol, applied to the three
remaining reviewer-named scenario groups.

## Context and approval chain

After Group 1's pilot (tie: both fresh-context naive policies matched the real rule
exactly), the user explicitly asked to pilot the three remaining scenario groups named by
the external review that proposed this methodology: obligation, multi-hop, and widening /
cross-vocabulary mapping ("(b) pilot thêm 3 nhóm còn lại"). The same four conditions from
the user's original instruction apply unchanged: (1) each naive policy is authored by a
fresh-context agent with no access to this repository, the paper, or this conversation --
only a one-page, jargon-free specification; (2) the specification is frozen (hashed,
timestamped) before any case generation; (3) all naive failures are reported, not just the
hardened baseline's FAR; (4) results are labeled honestly as a pilot with model-authored
policies, not a substitute for independent human authors.

## Grounding each group in a real, already-implemented system fragment

Per the same non-circularity discipline as Group 1, each spec was grounded in a fragment
of the chaincode that already exists and is already disclosed elsewhere in this project,
not invented for this pilot:

- **Group 2 (obligation).** `obligation_v2.go`'s mechanism-strength ordering
  (`notification=1, audit=2, dual_approval=3, combined=4`, required vs. mapped comparison)
  -- the general R_P checker's "obligation mechanism-strength" fragment from 2026-10-10.
  Spec: amounts above half of a role's cap require evidence of strength >= 3.
- **Group 3 (multi-hop).** `multihop_real.go`'s real `SubmitHopDecision` entry point,
  whose composed-context flag is the logical AND of every hop's own `contextAtHop` value
  propagated hop-by-hop through real on-chain reads -- the same file's
  `SubmitHopDecisionPairwiseLocal` ablation already demonstrates the real, known-bad
  variant (always SAFE once state-binding continuity holds, never examining the
  accumulated context). Spec: GRANT iff every element of a 1-5-length boolean list is
  true.
- **Group 4 (cross-vocabulary widening).** The real `RoleMapping` table
  (gerente->manager, gerente_senior->director) already studied via hand-designed Z3
  mutations in `rp_checker_tier.py` (2026-10-11, Trụ 4) -- this pilot instead tests it
  with a *fresh agent* under the same four conditions, on a vocabulary-translation
  framing (two extra filler source roles added so the five-row table is not trivially
  identifiable as "the real system's own three roles"), including an explicit
  fail-closed requirement for unmapped source roles.

None of the three specs mention Cedar, OPA, R_P, M_I, zero-knowledge proofs, or this
project by name; each is a free-standing, jargon-free page (`spec_v1.md` in each group's
directory). Freeze: SHA-256 hashes and a single UTC timestamp recorded for all three specs
before any agent was launched or any case generated (`FREEZE_HASHES.txt`,
`FREEZE_TIMESTAMP.txt`, 2026-10-11T10:33:40Z).

## What was actually done

1. Three one-page specs written and frozen (hash+timestamp) before any case generation or
   agent launch -- this time the freeze-then-generate ordering violation from Group 1 was
   not repeated.
2. Six fresh-context `general-purpose` agents launched in parallel (2 per group: one told
   to write Cedar, one told to write Rego/OPA), each given only its group's frozen spec
   pasted inline, explicitly instructed not to search the filesystem or assume any larger
   project. Each wrote its policy file plus a NOTES.md describing any choices the spec
   left open.
3. All six naive policies were read directly (not trusted from agent summaries) before any
   evaluation:
   - G2 naive Cedar: 10 explicit `permit` rules (two per role: evidence-free up to
     half-cap, evidence-gated from half-cap to cap requiring `dual_approval`/`combined`),
     relying on Cedar's default-deny for every reject case.
   - G2 naive OPA: `cap_map`/`half_cap_map`/`strength_map` lookup tables with an
     `else = 0` fallback for unrecognized evidence types.
   - G3 naive Cedar: represented `hops` as a Cedar `Set<Bool>` rather than an ordered
     list, with the NOTES.md explicitly justifying this as a lossless reduction for an
     AND-of-all rule (order- and duplicate-independent) -- a genuinely clever, correct
     simplification, not an error.
   - G3 naive OPA: `every hop in input.hops { hop == true }` with `import rego.v1`, a
     direct, idiomatic translation.
   - G4 naive Cedar and OPA: both a straightforward 5-row table lookup with fail-closed
     default-deny/undefined-lookup behavior for any unmapped `source_role`, including the
     deliberate trap case `source_role == "manager"` (a destination-side name that looks
     plausible but is not one of the five source-side table keys) -- both correctly denied
     it.
4. Hardened (full-knowledge) baselines written independently by me for all three groups,
   deliberately using representations NOT copied from the naive agents' output where that
   was feasible (e.g. Group 3's hardened Cedar uses five explicit per-index attributes
   `hop1..hop5` + `hop_count`, authored before reading the naive agent's `Set<Bool>`
   choice; both representations are carried side-by-side in the same evaluation context so
   each policy consumes only the keys it expects).
5. Mechanical case generation, independent of any naive/hardened file:
   - Group 2: 300 cases (5 roles x 10 boundary amounts x 6 evidence types including one
     unrecognized string), ground truth computed directly from the frozen spec.
   - Group 3: 63 cases -- this is an **exhaustive** enumeration of the entire finite
     domain (every boolean combination of length 1 through 5, plus the empty case), not a
     boundary sample, since the domain is small enough to enumerate completely.
   - Group 4: 56 cases (5 known + 3 unmapped source roles x 7 boundary amounts each).
6. Real-engine evaluation:
   - **OPA v0.70.0** (same binary as Group 1), via `opa eval` subprocess calls, one per
     case per policy. First run found a real bug in my own hardened Group 3 policy (see
     below); after the fix, 0/300, 0/63, 0/56 mismatches for every naive AND every
     hardened policy across all three groups.
   - **Cedar v4.13.0** (`cedar-policy` crate, same as Group 1), via a new Rust harness
     (`cedar_eval/`) built to evaluate all three groups in one binary. 0/300, 0/63, 0/56
     mismatches for every naive AND every hardened policy.
7. Exhaustive Z3 re-check for Groups 2 and 4 (Group 3 already exhaustively enumerated in
   step 5, so a separate Z3 pass there would be redundant and was not run), reusing
   `find_divergence()` from `rp_checker.py` unmodified, with independent Z3
   transcriptions of each naive file's own structure (not reusing the real rule's Z3
   object): `widening_found=False` and `over_conservative_found=False` for all four
   naive policies checked (G2 Cedar, G2 OPA, G4 Cedar, G4 OPA).

## A real bug found in my own hardened baseline (Group 3, OPA)

My first hardened OPA policy for Group 3 used the `every h in input.hops { h == true }`
construct without the required `import future.keywords.every` (the naive agent's own file
included `import rego.v1`, which brings in the same keyword implicitly -- I had not
noticed this when writing the hardened file independently). Real OPA reports this as a
**parse error written to stdout**, not stderr and not a clean `true`/`false` value; my
first evaluation harness treated any non-`true`/non-`false` stdout as an automatic
mismatch, which is why the first run reported 63/63 "mismatches" for the hardened policy
only (the naive policy, which had the correct import, showed 0). This was caught
immediately by the asymmetry (a hand-written "known-correct" baseline failing on literally
every case is a sign of a harness/baseline bug, not a naive-policy bug) -- the same kind
of tell that caught the Group 1 Cedar entity-namespace bug. Fixed by adding the import;
also hardened the harness itself to raise on a non-zero OPA exit code instead of silently
mapping any unexpected output to `False`, so a future parse error cannot masquerade as a
passing result.

## What this does and does not establish

This still does **not** establish that ADP's $R_P$/$M_I$ formalism is unnecessary in
general, nor that hand-written Cedar/OPA policies are reliably correct in general: N=1 per
engine per group, model-authored (not independently-recruited human) naive authors,
repo-isolation instructed but not technically enforced/verified, and only the four
scenario families the review named (not an exhaustive taxonomy of possible mapping
errors). What it does establish, honestly: across four independent, pre-registered,
disciplined pilots spanning four structurally different kinds of destination-local
authorization logic (threshold mapping, evidence-strength obligation, multi-hop boolean
aggregation, and cross-vocabulary table lookup with fail-closed defaults), zero errors
were found in any fresh-context naive policy, in either Cedar or OPA, by any of three
independent verification methods (code inspection, real-engine mechanical/exhaustive case
sweep, and exhaustive Z3 re-check). We therefore do not claim $R_P$/$M_I$ is necessary for
any of these four families either; the paper's claim remains the narrower one already
adopted after Group 1: ADP makes this class of mapping's correctness mechanically,
exhaustively verifiable (a Z3 certificate, not a sampled test), which a correct-or-not
Cedar/OPA policy does not supply for itself.

## Escalation status (user's own pre-specified triggers)

The user specified two triggers for escalating from this pilot ("phương án 1") to a full
human-authored, independently-labeled study ("phương án 2"): (a) the pilot shows naive
policies letting through errors the checker catches, or (b) at least two to three weeks
remain before the submission deadline. Trigger (a) has now not fired in **any** of the
four scenario groups piloted (0 errors across 489 total real-engine cases plus 2 exhaustive
Z3 checks plus one exhaustive enumeration). Trigger (b) was not evaluable by me (deadline
runway not stated in this conversation). Per the user's own stated logic, a 4-for-4 null
result does not by itself imply escalation is warranted -- but the user may reasonably
read four-for-four differently than one-for-one, which is why this is reported back for a
decision rather than acted on unilaterally.
