# E8, A9 built deeper: a real concurrent TOCTOU race, state-bound vs. caller-chosen time (2026-09-24)

`evidence/e8_remaining_ablations_2026-09-24.md` explained A9 (TOCTOU/state
binding) as not admitting a per-transaction ablated twin, since Fabric's
MVCC read-set validation is automatic for every `GetState` call and no
chaincode function can disable it. That remains true for `GetState`
generically -- but `clock.go`'s own real code contains a genuine,
pre-existing second path for exactly the freshness-relevant value at
stake: `ledgerNow(ctx)` normally reads the freshness clock via
`GetState(clock:now)` (real, version-tracked, genuinely bound into the
transaction's MVCC read-set), while its own `useLedgerClock` toggle (code
comment: "tests may disable") falls back to
`ctx.GetStub().GetTxTimestamp()` -- the caller's own chosen transaction
timestamp, which involves **no `GetState` call at all** and therefore adds
nothing to the read-set. This is a second, real, separately-invocable
mechanism, mirroring what made A7 buildable after all.

## Design

New, additive entry point (`ablation_a9_toctou.go`):
`SubmitDecisionTrustlessCallerTimestamp` is `SubmitDecisionTrustless` with
its time reference taken from `GetTxTimestamp()` instead of `ledgerNow()`
-- `verifySourceState` itself is reused completely unchanged; only how
"now" is obtained differs.

**Real test (genuine concurrency, not just an old value)**: fired the
decision submission and a `SetClock` call truly concurrently
(`subprocess.Popen`, not waited-for before the second call starts -- the
same concurrent-race pattern as the 2026-09-21 TOCTOU experiment and E4's
replay races), then decoded the actually committed blocks (not the CLI's
immediate response, which reflects only endorsement/simulation and looks
identical either way) to read the real validation code.

## Real results

| | Function | Concurrent with | Block | Validation code |
|---|---|---|---|---|
| Real | `SubmitDecisionTrustless` | `SetClock` | 405 | **11, `MVCC_READ_CONFLICT`** |
| Ablated | `SubmitDecisionTrustlessCallerTimestamp` | `SetClock` | 406 | **0, `VALID`** |

The real path's transaction genuinely read `clock:now` as part of its
simulation; the concurrent `SetClock` write to that same key, ordered
before it, caused Fabric to correctly invalidate it at commit --
real TOCTOU protection catching a real race. The ablated path's
transaction never called `GetState` for time at all, so it has no
read-set entry for `clock:now` whatsoever; the identical concurrent
`SetClock` activity had zero effect on it, and it committed successfully
regardless. **2/2 real transactions matched expectation.**

## Why this is a deeper result than A4's

A4 (freshness) showed that an already-stale value is rejected. This A9
result shows something structurally different: the *same* freshness
mechanism, under a *genuine concurrent race*, is caught by Fabric's real
optimistic concurrency control in one design and is architecturally
invisible to it in the other -- not because the ablated path's freshness
math is wrong, but because nothing about "now" is bound into its
transaction's read-set at all. This is precisely what "TOCTOU protection"
means: not merely rejecting stale data, but ensuring a check-then-act
sequence cannot be raced against.
