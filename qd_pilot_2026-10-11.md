# Disciplined pilot: fresh-context naive Cedar/OPA authors vs. the real tier→cap-fraction rule (2026-10-11)

This is the "phương án 1" pilot a further external review asked for, after correctly flagging
that `qd_necessity_demo_2026-10-11.md`'s forged-proof result conflates "a verification layer
$V$ is required" with "ADP's $R_P$/$M_I$ is necessary beyond a hand-written Cedar/OPA policy
consuming $V$'s output." That review proposed a full three-arm (Cedar+$V$, OPA+$V$, ADP) study
with 2-3 independent external human policy authors and third-party case labeling. The user
approved running a smaller, disciplined pilot now (not the full study), with four explicit
conditions: (1) the naive policy must be written in a completely fresh session with no repo
access, no knowledge of the S0-S19 scenarios, and no conversation history; (2) freeze the spec
and the naive policy (hash + timestamp) before generating test cases; (3) report every naive
failure, with the most informative number being how many naive-accepted cases a Z3 checker
(Corollary 1 / `rp_checker.py`) catches; (4) label the result honestly as a pilot with
model-authored policies, not a substitute for independent human authors, and not the paper's
main necessity claim.

**Scope of this pilot**: Scenario Group 1 only (mapping error: the tier→role-cap-fraction
table), the group the existing risk-tier $R_P$ instance and `rp_checker_tier.py` already cover.
Groups 2 (obligation), 3 (multi-hop freshness) and 4 (cross-vocabulary widening) from the
reviewer's four-group design are **not** run in this pilot.

## What was actually done

1. **Specification, frozen.** `spec_v1.md` -- a plain-English, ADP-jargon-free one-pager
   (role caps, tier→fraction table, grant rule) handed to a policy author with no other context.
   `sha256(spec_v1.md) = 544237e7b44d06ae1e0397ccd90620bb2daa9ee0b8a2dd25d99949a84d96917f`,
   recorded at `2026-10-11T09:20:01Z`, before either naive-author agent was launched.

2. **Two independent fresh-context agents**, launched via this session's `Agent` tool with
   `subagent_type: general-purpose` (a fresh agent starts with *zero* conversation context --
   it has not seen this paper, the chaincode, or any earlier review in this session). Each was
   given only `spec_v1.md`'s text, pasted into its prompt (not a file path into the repo), and
   explicitly instructed not to Grep/Glob/`find`/`git` or read any file beyond its own output
   path. One wrote a Cedar policy, the other a Rego policy; neither was told about the other or
   about any evaluation that would follow. This approximates, but does not fully guarantee, the
   "no repo access" condition: both agent types retain `Bash`/`Read` tool access and could in
   principle have disobeyed the instruction and explored the filesystem; this was not
   separately audited (e.g. by inspecting each agent's tool-call transcript for an unauthorized
   `Read`/`Bash find` on project files) and is disclosed as a real limitation of this proxy for
   "a fresh human author," not a verified guarantee.

3. **Naive policies received and read directly** (not taken on the agents' own summary):
   `naive_cedar/policy.cedar` and `naive_opa/policy.rego` (verbatim copies in this directory).
   Both independently reproduce the spec's five role caps and the tier→fraction table exactly
   (clerk $10k/manager $500k/director $2M/gerente $500k/gerente_senior $2M;
   tier 1→10%, tier 2→50%, tier 3→100%, tier 0→deny), with no swap, reversal, or off-by-one
   found on inspection.

4. **Process-discipline gap, disclosed rather than silently corrected**: condition (2) asked
   for freezing spec + naive policy (hash + timestamp) *before* generating test cases. In
   practice, the naive policies were read (step 3) before the mechanical case generator
   (`cases.json`) was written -- the hash/timestamp below were recorded late, not before case
   generation. The case generator is driven entirely by `spec_v1.md`'s own parameters (role
   caps and tier boundaries), not by anything in the naive files, so there is no plausible
   mechanism by which having read the naive policies first could have biased which cases were
   generated toward or away from any particular outcome -- but the actual execution order did
   not match the pre-registration discipline asked for, and this is stated plainly rather than
   reordered in the writeup to look compliant.
   `sha256(naive_opa/policy.rego) = 65eea4fe8cf767bebad6a7f189ee8df6a774cb2e6ee1a6991c67b17baa5a0ce7`,
   `sha256(naive_cedar/policy.cedar) = 49ea35e8c06d512c5581e6dfeba015012b17a08f99c0fe53d8af13c0f47ed6ef`,
   `sha256(cases.json) = eec20724dbc85dfec3cf7aaf0986b27cb225d1d40053e1a37dc2c883a43ddcca`,
   recorded `2026-10-11T09:26:26Z`.

5. **Mechanical boundary-value case set** (`cases.json`, 70 cases, same style as
   `rp_checker_tier.py`'s naive-variant boundary points and the project's earlier mechanical
   sweeps -- no AI-adversarial content): for each of the 5 roles × tier 0 (always-deny, amount
   ∈ {1, cap}) and tier ∈ {1,2,3} (amount at the exact cap-fraction boundary, one dollar under,
   one dollar over, and a trivial $1 amount) = 70 cases, each labeled with the real expected
   GRANT/DENY from the spec's own rule computed independently in Python.

6. **Hardened baseline, written by me (full knowledge)**: `hardened_cedar/policy.cedar`,
   `hardened_opa/policy.rego` -- the upper-bound arm, never shown to the naive-author agents.

7. **Real engines, all four policies run against all 70 cases**: OPA v0.70.0 (`opa eval`,
   `opa_results.json`) and Cedar v4.13.0 (`cedar-policy` Rust crate, `cedar_results.json`).
   **A real bug was found in my own hardened Cedar policy during this step, not in either
   naive policy**: my first `hardened_cedar/policy.cedar` scoped its `permit` to
   `principal == User::"submitter", action == Action::"submit", resource == Decision::"d"` --
   copied from an earlier, unrelated pilot file (`qd_necessity_demo_2026-10-11`'s driver) --
   while the evaluation harness (built to match the naive Cedar agent's own chosen entity
   namespace, `DestinationAuth::...`) sent requests with different entity UIDs. Cedar's scope
   match failed on every request, so every case fell through to Cedar's default-deny: 45/70
   false DENY on the hardened arm, 0 on the naive arm, on the first run. Caught by the
   asymmetry (a hand-written "obviously correct" policy failing more than the blind one), not
   assumed benign; root-caused to the entity-namespace mismatch and fixed by widening the
   hardened policy's scope clause to match the harness's actual entities. Disclosed in full
   rather than quietly re-run and reported only with the fixed numbers.

8. **Formal, exhaustive check via the existing general $R_P$ Z3 checker** (`z3_check_naive.py`,
   reusing `find_divergence()` from `rp_checker.py` -- the same function behind Corollary 1,
   2026-10-10 -- unmodified). Both naive policies were transcribed into **independent** Z3
   expressions matching each file's own internal structure (the OPA policy's `num`/`den`
   integer-fraction form; the Cedar policy's nested nested-if per-role threshold table) rather
   than re-using the real rule's own Z3 object, so the check is not circular by construction.
   `find_divergence` checks both directions: *widening* (naive accepts something the real rule
   rejects -- an unsafe accept) and *over-conservative* (naive rejects something the real rule
   accepts), over the full integer domain (amount 1..20,000,000, not just the 70 sampled
   points).

## Results

| Check | naive_opa | naive_cedar | hardened_opa | hardened_cedar |
|---|---|---|---|---|
| 70-case engine run, mismatches vs. real rule | **0/70** | **0/70** (after the hardened-arm bug above was fixed) | 0/70 | 0/70 |
| Z3 `find_divergence`, widening (unsafe accept) | **not found** | **not found** | n/a (not Z3-checked; by-construction identical to the real rule) | n/a |
| Z3 `find_divergence`, over-conservative | **not found** | **not found** | n/a | n/a |

**This pilot is a tie for Scenario Group 1.** Neither fresh-context naive author introduced a
mapping error: both the 70-case boundary sweep on the real engines and the exhaustive Z3 check
found zero divergence from the real rule, in either direction, for either language. The
"informative number" condition (3) asked for -- naive cases the Z3 checker catches -- is **0**.

## Interpretation (per the user's pre-agreed reading rules)

This is the outcome the synthesizing review explicitly anticipated and gave instructions for:
*"Baseline gia cố bắt được ngang ADP... Hòa hoàn toàn ở mọi nhóm: hãy thừa nhận, và chuyển
trọng tâm của bài sang mô hình cộng các lỗi ghép nối đã tìm ra, không nói ADP là 'cần thiết'."*
For this one group, that is the honest result: a careful fresh author, given a clean,
unambiguous one-page spec, transcribed a 5-role × 4-tier lookup-and-threshold rule correctly in
both Cedar and Rego. This is evidence about this *kind* of rule (a stateless, purely
declarative mapping with no cross-system binding, no proof/witness handling, and no time or
replay state), not evidence that Cedar/OPA can express every check this paper's $R_P$
instances need -- Groups 2-4 (obligation discharge state, multi-hop freshness against an
origin timestamp carried across hops, cross-vocabulary widening where the two policies'
predicates are stated over structurally different domains) were not run and are exactly the
kinds of check a stateless attribute-based policy-evaluation language is least suited to
express, unlike a flat lookup table.

**What this pilot does, and does not, license saying in the paper**: it licenses saying that
ADP's formal $R_P$ apparatus (`rp_checker.py`/Corollary 1) gives a destination a way to know,
with an exhaustive proof over the full integer domain, that its tier→fraction table is sound --
a guarantee neither naive nor hardened Cedar/OPA, taken alone, supplies for itself (a Cedar/OPA
policy that happens to be correct carries no internal certificate of that fact; this pilot's
own "0/70, not found" verdict required building and running a separate Z3 encoding against it).
It does **not** license saying a hand-written Cedar/OPA policy is less likely to get this
particular kind of rule right in practice -- the one data point here says it is not.

## Scope and limitations (stated in full, not minimized)

- **N=1 per engine**, not the 2-3 independent authors the full study design calls for; one
  naive-author agent per language could have gotten it right by chance on a rule this simple.
- **Model-authored, not human-authored.** The "naive" authors are fresh instances of the same
  underlying model family as the one running this pilot, not independent human policy
  engineers; a real external reviewer's hardest question ("does a model-authored policy
  represent a real administrator?") is not answered by this pilot and is not claimed to be.
- **Repo-isolation was instructed, not verified.** See point 2 above: both agents retained tool
  access that could have let them look beyond the spec; this was not independently checked.
- **Pre-registration ordering was not followed exactly**: naive policies were read before the
  test-case generator was written (point 4 above), though the generator's parameters come only
  from the spec, not from the naive files.
- **One scenario group only** (mapping error). Groups 2-4 (obligation, multi-hop freshness,
  cross-vocabulary widening) -- plausibly the harder cases for a stateless policy-evaluation
  language -- were not attempted in this pass.
- **A tie on this group does not establish, and is not used to argue, that $R_P$/$M_I$ is
  unnecessary** -- the same caution applies in reverse: this result alone also does not
  establish necessity. It establishes exactly what is reported above and no more.

## Escalation condition (per the user's own instruction)

The user specified two triggers for moving to the fuller human-authored, third-party-labeled
study ("phương án 2"): the pilot showing naive policies let through many errors the checker
catches, or at least 2-3 weeks remaining before the submission deadline. **Neither trigger was
met by this run**: 0 naive errors were found in Group 1. All pilot materials (spec, freeze
hashes, case generator, both policy pairs) are reusable unchanged for a Group 1 round of
"phương án 2," and for extending to Groups 2-4, if the user chooses to proceed regardless.
